## TLDR

[REPORTED] MiroFish describes itself as a “simple and universal swarm intelligence engine” that extracts seed information, builds a graph-backed digital world, creates many agents with personas and memory, runs social evolution, and produces a prediction report plus an interactive world. [VERIFIED, [README workflow](https://github.com/666ghj/MiroFish/blob/main/README.md#-workflow)]

[VERIFIED] The implemented path is more specific than the slogan: uploaded documents and a natural-language `simulation_requirement` become an LLM-generated ontology; text is chunked into a Zep Cloud Standalone Graph; typed graph entities are filtered and turned into OASIS/Twitter/Reddit profiles; another LLM generates simulation parameters; OASIS runs the two social platforms; actions can be appended back to the graph; and a Report Agent retrieves graph facts and interviews simulated agents. [VERIFIED, [graph API](https://github.com/666ghj/MiroFish/blob/main/backend/app/api/graph.py), [graph builder](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py), [simulation manager](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_manager.py), [parallel runner](https://github.com/666ghj/MiroFish/blob/main/backend/scripts/run_parallel_simulation.py), [Zep tools](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py)]

[INFERRED] The strongest FalconOS transfer is not “simulate a market.” It is a staged brain pipeline: typed entities/relations, temporal current-versus-history retrieval, explicit intent/config records, bounded multi-agent research, and durable tool/action traces. The weakest transfer is evidence authority: MiroFish's graph is LLM-extracted and its reports are generated prose, whereas FalconOS requires canonical hashed snapshots, strict `READY`/`NO_DATA`, and fail-closed advisory output. [INFERRED, [FalconOS perps contracts](../perps/perps.ts), [stocks contracts](../stocks/stocks.ts), [agent contracts](../src/agent.ts)]

## Architecture and lifecycle

### 1. Project/intent intake

[VERIFIED] The graph API accepts PDF/Markdown/text uploads, a required natural-language `simulation_requirement`, optional project name, and optional additional context. It stores source files and extracted text in a project directory, then calls `OntologyGenerator.generate(document_texts, simulation_requirement, additional_context)`. [VERIFIED, [graph API lines 263-380](https://github.com/666ghj/MiroFish/blob/main/backend/app/api/graph.py#L263-L380), [project model](https://github.com/666ghj/MiroFish/blob/main/backend/app/models/project.py#L26-L104)]

[VERIFIED] The persisted project record is a JSON-backed state object containing project status, file metadata, extracted-text length, ontology, analysis summary, graph ID, durable Zep batch identity, `simulation_requirement`, chunk settings, timestamps, and errors. The lifecycle is `created -> ontology_generated -> graph_building -> graph_completed` or `failed`. [VERIFIED, [project model](https://github.com/666ghj/MiroFish/blob/main/backend/app/models/project.py#L17-L104)]

[INFERRED] This is a useful intent-record precedent for FalconOS: preserve the user's research question, source set, graph/snapshot identifiers, generation parameters, and lifecycle state as one immutable-or-versioned request envelope rather than passing a free-form prompt between agents. [INFERRED, [project model](https://github.com/666ghj/MiroFish/blob/main/backend/app/models/project.py#L26-L104)]

### 2. LLM-generated ontology

[VERIFIED] The ontology prompt requires JSON with `entity_types`, `edge_types`, and `analysis_summary`; entity types contain name, description, attributes, and examples; edges contain name, description, source-target pairs, and attributes. The prompt is domain-specific: entities are real actors that can speak/interact on social media, while abstract concepts such as “trend” or “sentiment” are explicitly disallowed as entities. [VERIFIED, [ontology prompt](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/ontology_generator.py#L47-L191)]

[VERIFIED] The prompt asks for exactly ten entity types, with `Person` and `Organization` fallbacks, six-to-ten relation types, and one-to-three key attributes per type. The validator normalizes names, removes duplicates/unusable entries, caps ontology types at ten, caps attributes at ten, caps source-target pairs at ten, and adds fallback attributes when an entity has none. [VERIFIED, [ontology generator](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/ontology_generator.py#L432-L535), [ontology limits](https://github.com/666ghj/MiroFish/blob/main/backend/app/utils/ontology.py)]

[VERIFIED] Reserved attribute names include `uuid`, `name`, `group_id`, `graph_id`, `name_embedding`, `summary`, and `created_at`; invalid or empty source-target pairs are removed and duplicate pairs are deduplicated. [VERIFIED, [ontology utility](https://github.com/666ghj/MiroFish/blob/main/backend/app/utils/ontology.py)]

[INFERRED] The valuable design choice is schema-before-ingestion: the LLM proposes a constrained ontology, the host normalizes it, and only then does ingestion occur. FalconOS can use the same shape for a knowledge graph of instruments, venues, protocols, catalysts, claims, risks, and evidence—but should not force a fixed ten-type limit or allow an LLM to silently define authority-bearing fields. [INFERRED, [ontology utility](https://github.com/666ghj/MiroFish/blob/main/backend/app/utils/ontology.py), [FalconOS strict validators](../perps/perps.ts)]

### 3. Graph construction and knowledge-base schema

[VERIFIED] `GraphBuilderService` creates a Zep Standalone Graph, installs dynamic Pydantic entity and edge classes from the ontology, splits source text (default chunk size 500 and overlap 50), submits chunks through Zep Batch API, waits for terminal processing, then counts nodes/edges/types. [VERIFIED, [graph builder](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L75-L211), [ontology installation](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L313-L405)]

[VERIFIED] The graph projection exposes node records with `uuid`, `name`, `labels`, `summary`, `attributes`, and creation time. Edge records expose `uuid`, `name`, `fact`, `fact_type`, source/target UUID and names, attributes, creation/valid/invalid/expired times, and episode IDs. [VERIFIED, [graph data](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L777-L875)]

[VERIFIED] Entity filtering keeps nodes with custom labels beyond default `Entity`/`Node`; each retained entity can carry outgoing/incoming edge facts and neighboring-node summaries. Full-graph pagination is used when complete incoming and outgoing context is required. [VERIFIED, [entity reader](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_entity_reader.py#L168-L219), [filtering](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_entity_reader.py#L221-L337)]

[VERIFIED] Ingestion adds deterministic operation metadata: an operation ID hashes the graph ID and all chunks; each chunk carries a SHA-256 hash and chunk index; batch metadata records operation ID, graph ID, and chunk count. The builder validates Zep limits before mutation, including at most 350 items per batch, 50,000 total items, and 10,000 characters per item. [VERIFIED, [graph builder operation identity](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L263-L311), [batch ingestion](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L407-L580)]

[INFERRED] These hashes are ingestion/reconciliation identities, not FalconOS-grade canonical evidence hashes: they do not authenticate the extracted fact, prove source integrity at report time, or bind a claim to a signed snapshot. Reuse the “hash before mutation + durable operation ID” pattern, but keep authority in FalconOS canonical snapshot bytes and receipts. [INFERRED, [graph builder](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L263-L311), [FalconOS perps hashing](../perps/perps.ts), [FalconOS stock hashing](../stocks/stocks.ts)]

### 4. Simulation preparation and intent/config records

[VERIFIED] `SimulationManager.prepare_simulation` reads and filters graph entities, generates one profile per entity (optionally with LLM enrichment and parallel profile generation), then invokes `SimulationConfigGenerator.generate_config` with the simulation requirement, original document text, graph ID, and filtered entities. [VERIFIED, [simulation manager](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_manager.py#L244-L365)]

[VERIFIED] `SimulationParameters` is a structured intent/config record containing simulation/project/graph IDs, the original `simulation_requirement`, time configuration, per-agent configurations, event configuration, platform configurations, LLM model/base URL, generation timestamp, and free-text `generation_reasoning`. It serializes to JSON in the simulation directory. [VERIFIED, [simulation config schema](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L52-L198), [config persistence](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_manager.py#L404-L463)]

[VERIFIED] Per-agent generated fields include entity UUID/name/type, activity level, posts/comments per hour, active hours, response delay bounds, sentiment bias, stance, and influence weight. Event fields include initial posts, scheduled events, hot topics, and narrative direction. Platform fields include recency/popularity/relevance weights, viral threshold, and echo-chamber strength. [VERIFIED, [config dataclasses](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L52-L146)]

[VERIFIED] Generation is staged: time config, event config, agent configs in batches of fifteen, initial-post publisher assignment, and platform defaults. The context includes the requirement, entity summaries, and a bounded prefix of document text; LLM calls use JSON mode, retries, temperature reduction, and JSON-repair/default fallbacks. [VERIFIED, [generation pipeline](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L201-L380), [bounded context](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L382-L483)]

[INFERRED] FalconOS should borrow the explicit typed intent record and staged generation, but make every generated field either advisory metadata or a rejected/blocked proposal. A generated `stance` or `influence_weight` may guide research prioritization; it must never become a trading instruction, allocation, signer request, or execution permission. [INFERRED, [FalconOS agent contract](../src/agent.ts), [FalconOS types](../src/types.ts)]

### 5. Agent orchestration and social dynamics

[VERIFIED] The runner starts external OASIS scripts for Twitter, Reddit, or both in parallel. The scripts import OASIS/CAMEL, build platform agent graphs, and restrict the available action sets to social actions such as post, like, repost, follow, comment, search, mute, trend, refresh, and no-op. [VERIFIED, [parallel runner](https://github.com/666ghj/MiroFish/blob/main/backend/scripts/run_parallel_simulation.py#L158-L202)]

[VERIFIED] Runtime state is represented by `AgentAction`, `RoundSummary`, and `SimulationRunState`. Actions record round, timestamp, platform, agent ID/name, action type/arguments, result, and success; round summaries record simulated hour, platform action counts, active agents, and action lists; run state tracks progress, per-platform completion, recent actions, timestamps, process ID, and errors. [VERIFIED, [simulation runner](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_runner.py#L56-L201)]

[VERIFIED] The runner uses persisted `state.json`/`run_state.json`, process/thread registries, bounded finalization locks, explicit statuses, signal/atexit cleanup, and an IPC wait mode after simulation completion. Interview commands can target one agent, a batch, or all configured agents, and can query both platforms. [VERIFIED, [simulation manager](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_manager.py#L44-L206), [runner lifecycle](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_runner.py#L204-L500), [interviews](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_runner.py#L604-L841)]

[VERIFIED] The simulation configuration explicitly models opinion/diffusion-like dynamics through sentiment bias, stance, influence weight, platform ranking weights, viral thresholds, and echo-chamber strength. [VERIFIED, [simulation config schema](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L52-L146)]

[REPORTED] The README mentions financial prediction as a future example, but the inspected implementation is a social-media opinion simulation over Twitter/Reddit and does not expose a market-price, order-book, portfolio, or trading simulator. [VERIFIED/REPORTED, [README](https://github.com/666ghj/MiroFish/blob/main/README.md), [runner action sets](https://github.com/666ghj/MiroFish/blob/main/backend/scripts/run_parallel_simulation.py#L177-L202)]

### 6. Dynamic graph memory

[VERIFIED] `ZepGraphMemoryUpdater` consumes successful OASIS actions, skips `DO_NOTHING` and failed events, converts actions into natural-language episode text with timestamps/platform/round, batches five activities per platform, and writes them to the graph with metadata for simulation ID, platform, activity count, round range, agent IDs, and action types. [VERIFIED, [activity model](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L25-L67), [updater](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L213-L241), [batch write](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L444-L548)]

[VERIFIED] Updater shutdown drains queues and buffers, refuses to silently replay ambiguous non-idempotent `graph.add` writes, records failed batches, waits for returned episode UUIDs to become processed, and keeps failed updaters registered so lifecycle/report/deletion guards can see incomplete ingestion. [VERIFIED, [updater stop/failure behavior](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L313-L348), [non-idempotent write handling](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L488-L621)]

[INFERRED] This is a strong “append event, then project into graph” pattern for FalconOS research memory. The event should remain the durable source record; graph extraction is a derived index. For FalconOS, the event must additionally carry source URL, capture time, parser version, content hash, evidence class, and snapshot ID so a graph edge can be traced back to canonical evidence. [INFERRED, [updater metadata](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_graph_memory_updater.py#L494-L517), [FalconOS source contracts](../perps/perps.ts)]

### 7. Retrieval, interviews, and evidence handling

[VERIFIED] Zep tools expose typed result records for semantic search, node/edge details, deep `InsightForge`, broad `Panorama`, and `Interview`. Search asks Zep for hybrid semantic+BM25 retrieval with cross-encoder reranking; results preserve facts, nodes, edges, query, and counts. [VERIFIED, [Zep tools result types](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L32-L130), [search](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L406-L500)]

[VERIFIED] `InsightForgeResult` carries generated sub-queries, semantic facts, entity insights, relationship chains, and counts. Its text rendering explicitly labels key facts for report quotation. `PanoramaResult` separates active facts from historical/expired facts and includes temporal edge fields. [VERIFIED, [InsightForge](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L143-L216), [Panorama](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L219-L286)]

[VERIFIED] Interview retrieval loads generated profiles, asks an LLM to select diverse relevant agents, generates three-to-five questions when none are supplied, calls the real OASIS batch-interview API across both platforms, preserves each platform's response, extracts key quotes, and asks another LLM for a neutral summary. [VERIFIED, [interview pipeline](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L502-L707), [selection/questions](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L776-L961)]

[VERIFIED] The report API refuses generation while simulation or Zep ingestion is active, requires a successfully completed or stopped run, requires a completed project graph, checks that simulation and project still reference the same graph, and registers the report as a graph reader during background generation. [VERIFIED, [report preconditions](https://github.com/666ghj/MiroFish/blob/main/backend/app/api/report.py#L32-L300)]

[REPORTED] `report_agent.py` describes a LangChain+Zep ReACT workflow: plan an outline, generate sections with iterative thought/tool calls, and support chat where the agent can invoke retrieval tools. The file's logger records report start, planning context, section starts, ReACT thoughts, tool calls/results, LLM responses, section content, errors, and completion in JSONL. [VERIFIED/REPORTED, [report agent](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/report_agent.py), [report API](https://github.com/666ghj/MiroFish/blob/main/backend/app/api/report.py#L589-L650)]

[INFERRED] MiroFish has useful evidence *provenance traces*—raw search result structures, graph episode metadata, tool logs, interview transcripts, and section boundaries—but it does not, in the inspected report path, establish claim-level signed citations or a canonical snapshot hash that binds every sentence to immutable source bytes. The “quote key facts” instruction is not equivalent to evidence validation. [INFERRED, [Zep tools](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py), [report agent](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/report_agent.py), [FalconOS agent thesis validation](../src/agent.ts)]

[VERIFIED] Retrieval and interview code has convenience fallbacks: graph search may fall back to local keyword matching when Zep search is unavailable, and LLM agent-selection/question/summary failures can fall back to default selection, canned questions, or concatenated summaries. [VERIFIED, [search fallback](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L457-L500), [interview fallbacks](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L830-L961)]

[INFERRED] Those fallbacks are acceptable for an exploratory sandbox but violate FalconOS's strict `BLOCKED`/`NO_DATA` posture unless explicitly labeled as degraded, confidence-reducing evidence and prevented from producing an actionable advisory. [INFERRED, [FalconOS snapshot statuses](../perps/perps.ts), [FalconOS stock statuses](../stocks/stocks.ts), [FalconOS types](../src/types.ts)]

## FalconOS mapping

### Brain / knowledge base

[INFERRED] Adopt a MiroFish-like typed graph as a derived research index: nodes for assets, venues, protocols, actors, catalysts, risks, claims, and documents; edges for “mentions,” “affects,” “contradicts,” “supports,” “expires,” and “derived-from.” Keep the event/document/evidence record authoritative and make graph edges point to immutable IDs plus hashes. [INFERRED, [MiroFish graph schema](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py#L800-L875), [FalconOS vault](../src/vault.ts)]

[INFERRED] Adopt three retrieval views inspired by MiroFish: (1) focused semantic retrieval for a question, (2) panorama retrieval that preserves current and historical claims, and (3) entity/relationship neighborhood retrieval. Every view should return evidence IDs, source hashes, capture timestamps, freshness/expiry, and explicit missing-data reasons—not only prose. [INFERRED, [MiroFish retrieval types](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L143-L286), [FalconOS source contracts](../perps/perps.ts)]

[INFERRED] An Obsidian-style human-facing graph can export these records as Markdown notes and links, but the graph/export must remain a view over the canonical evidence ledger, consistent with the existing FalconOS Obsidian study's local-first and hash-authority guidance. [INFERRED, [Obsidian study](./obsidian.md), [FalconOS vault](../src/vault.ts)]

### Continuous opportunity discovery

[INFERRED] Reuse MiroFish's seed -> ontology -> graph -> retrieval loop as a discovery loop: ingest a bounded source batch, normalize entities/relations, generate candidate opportunities/questions, retrieve counter-evidence and history, then emit a typed advisory candidate or `NO_DATA`. Do not import its social simulation as a market forecaster; MiroFish has no observed market-data or trading-evaluation layer in the inspected code. [INFERRED, [MiroFish workflow](https://github.com/666ghj/MiroFish/blob/main/README.md#-workflow), [simulation config](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L148-L198)]

[INFERRED] A candidate should store the originating intent ID, source-set/snapshot IDs, graph query/sub-queries, supporting and contradicting evidence, freshness horizon, assumptions, and invalidation conditions. This extends MiroFish's `generation_reasoning` and tool logs into a form the FalconOS Council can replay and audit. [INFERRED, [MiroFish config record](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L148-L198), [FalconOS agent thesis fields](../src/agent.ts)]

### Intent records

[INFERRED] Model an intent record after `Project` plus `SimulationParameters`: stable intent ID, user question, domain (`perps`/`stocks`), allowed read-only sources, graph/snapshot references, schema version, generated plan, model metadata, expiry, status, and failure reason. Persist the exact normalized request and hashes before dispatching research agents. [INFERRED, [MiroFish project model](https://github.com/666ghj/MiroFish/blob/main/backend/app/models/project.py#L26-L104), [MiroFish simulation parameters](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L148-L198), [FalconOS agent request](../src/agent.ts)]

[INFERRED] Treat LLM-generated sub-queries and interview questions as proposed research-plan data, not authority. Host code should cap counts, validate domains, record all queries, and fail closed when required evidence is missing or stale. [INFERRED, [MiroFish InsightForge](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/zep_tools.py#L143-L216), [FalconOS failure types](../src/types.ts)]

### Council advisory and current modules

[INFERRED] `perps/perps.ts` and `stocks/stocks.ts` should remain the source of truth for market snapshot schemas, provenance (`live`/`synthetic`/`historical`), SHA-256 content identity, deep-frozen canonical data, and `READY`/`NO_DATA`. MiroFish-derived research can enrich context or explain catalysts, but must not override a market field or turn simulated sentiment into a price fact. [INFERRED, [perps contract](../perps/perps.ts), [stocks contract](../stocks/stocks.ts)]

[INFERRED] `dash/council.ts` is the right seam for a lead specialist to consume graph-backed evidence and for a veto-only risk reviewer to reject stale, conflicting, unsupported, or non-advisory output. The dashboard/render layer should show evidence links, timestamps, hashes, query/intent IDs, and blocked reasons; it should never show simulated social actions as execution-ready actions. [INFERRED, [Council adapter](../dash/council.ts), [dashboard render](../dash/render.ts)]

[INFERRED] The Council kernel should borrow MiroFish's staged orchestration—plan, parallel retrieval/research, deterministic host aggregation, synthesis, and full trace—but preserve FalconOS's lead-plus-veto topology rather than adding a swarm vote. The Client Agent remains the only execution owner, and the current Falcon Investment Council remains advisory-only/read-only. [INFERRED, [FalconOS agent kernel](../src/agent.ts), [FalconOS types](../src/types.ts)]

### Does not transfer

[INFERRED] Do not transfer OASIS/Twitter/Reddit action loops, social persona generation, echo-chamber/viral parameters, IPC interview commands, or “prediction” language into execution or custody paths. They model simulated opinion behavior, not market microstructure, fills, funding, liquidity, corporate actions, or portfolio risk. [INFERRED, [MiroFish runner](https://github.com/666ghj/MiroFish/blob/main/backend/scripts/run_parallel_simulation.py#L158-L202), [config schema](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/simulation_config_generator.py#L52-L146)]

[INFERRED] Do not treat Zep Cloud as FalconOS's canonical store without an authority wrapper: external graph availability, LLM extraction, mutable local JSON state, provider fallback behavior, and generated prose all need explicit status/error boundaries. [INFERRED, [MiroFish graph builder](https://github.com/666ghj/MiroFish/blob/main/backend/app/services/graph_builder.py), [FalconOS vault](../src/vault.ts)]

## Lessons

- [VERIFIED] Schema-first ontology generation plus host-side normalization makes free-form source material queryable, but FalconOS should choose authority-bearing schemas itself.
