Decision to approve

Consumer task

PROPOSED: put CFO before legacy empty panels. Show actual USDC and receipt balances with their cutoff. Selecting an approved investment or held position supplies action context. Ask for one exact human-unit amount, or an explicit saved-allocation choice where supported. Show the backend plan and review, then the exact quote before signing.

PROPOSED: one primary action reflects the current state. A signature is not submission. Submission is not settlement. Uncertain actions show reconciliation and keep dependent funds reserved.

One-time setup

PROPOSED: offer “Use consumer template” in a separate limits panel. Copy six approved values into a local draft only. The owner still enters the protected USDC amount and per-move cap, chooses permissions/weights, reviews all values, and explicitly saves.

NON-GOALS: cash-slider-first landing, a mandatory multi-page wizard, hardcoded dollar shortcuts, invented NAV/PnL/APY, new funding rails, embedded wallets, automatic financial actions or hidden policy defaults.

Baseline and trade-off: the current form is complete but exposes policy and API mechanics on every visit. R5 keeps the existing complete mandate contract and moves it out of the daily task. It adds no new service, mutation route or database schema.

Detailed call paths and asynchronous boundaries

1. One-time policy copy and save

PROPOSED: the template response is static metadata. Owner review and the existing Save remain separate. Saving still requires the existing live provider-asset validation. The diagram shows a first save; duplicate handling is described below.

VERIFIED retries retained: same request ID and same body return the stored mandate. Reusing an ID for different content conflicts. After an ambiguous save, retry the original request in the mounted session or inspect retained state; never treat a local template selection as proof of save. Reload loses the current in-memory retry map, so no cross-reload exactly-once claim is made. Explicitly saving a new record can invalidate older plans even when values match.

2. Prepare once, then load exact review bounds

PROPOSED: after the existing prepare response, perform a GET-only retained-state refresh and correlate the exact logical action ID. This refresh creates no new capture, quote, model run, signature or submission. Existing unsigned-expiry and blocked-rotation housekeeping can still append state transitions.

PROPOSED signature gate: matching action ID, current unsigned action state, matching mandate/portfolio, valid quote hash, exact debit/assets, minimum output, required costs, destination and unexpired deadline. Missing or stale data blocks the wallet prompt. Show minimum versus estimated output distinctly. Keep raw payload unchanged in details; sign the exact original bytes.

VERIFIED authority retained: signature registration, separate relay confirmation, exact operator trial and reconciliation remain the R1/R2 paths. A lost signature-registration or relay reply is not permission to sign/send again. SIGNED, SUBMITTED, PENDING, UNVERIFIED and SUBMISSION_UNKNOWN remain distinct. Every rotation entry requires its own fresh quote, review and signature.

Data and state rules

  • PROPOSED: convert decimal text using verified token precision and integer/string operations only. Reject negative, zero action amounts, exponent notation and excess precision. Preserve values beyond JavaScript safe integer range. No money rounding or default amount.
  • PROPOSED: context and IDs come from observed owner portfolio plus saved permissions. The reserve is the buy source and redeem destination. If metadata is unavailable, do not guess it or render missing balances as zero.
  • PROPOSED: deduplicate action transitions by logical action ID, choose unresolved heads first, and retain full history in details. Do not calculate free cash by subtracting locally inferred reservations.
  • PROPOSED: template use marks only its draft fields dirty. Refresh cannot overwrite dirty choices. Wallet/session change clears action drafts and rejects late responses. Preset changes never rewrite a saved mandate.
  • VERIFIED limitation: capture provides supported token quantities, not complete USD NAV, APY or PnL. Do not create portfolio totals or returns from those quantities.

Unchanged blockers: 1Click data-retention terms versus indefinite unused-quote history; provider accounts/keys/terms; real review budget/pair; T82; exact capped mainnet trial; CI/publication/deployment approval. R5 does not solve or waive these.

Least confident decisions

  1. Template provenance: R5 deliberately persists approved numeric values, not a template adoption identity. If historical named-template attestation becomes required, it needs a separate explicit storage/API decision.
  2. First-use investment permissions: the current mandate still requires explicit target/weight choices to enable its allocation behavior. R5 removes repeated configuration and raw units; it does not invent allocation preferences.
