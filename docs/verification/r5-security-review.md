## Findings and launch gates

### [HIGH | launch blocker] Provider quote retention conflicts with published retention terms

Evidence **[VERIFIED SOURCE]**: `docs/interfaces.md:23` records the 1Click Terms of Service §4.1(e) limit of 24-hour API-data storage, except static end-user transaction history, and says R1 retains unexecuted quote snapshots without a retention limit. `mesh/cfo/service.mjs:880-885` appends quote envelopes to CFO history before plan creation; `mesh/cfo/store.mjs:523-540` lists records by owner and sequence but contains no retention bound in that read path. `README.md:19` records the same release gate.

**[INFERRED]** Risk: enabling live provider access while unexecuted provider quote data remains indefinitely retained would conflict with the documented terms unless a written exception or approved retention design applies. This is a provider-terms and data-retention gate; it is not evidence that an unauthorized live request occurred.

Required proof/action before provider activation: obtain and retain a written provider exception or approve and verify a retention/deletion design that meets the terms. Prove it against the actual retained quote records and owner history, including recovery/replay paths. Do not treat local fixtures or an R5 UI change as closing this gate.

Severity basis: High launch blocker while provider activation is gated; no live violation is asserted.

### [HIGH | launch blocker] Do not treat service readiness or a selected profile as execution readiness

Evidence **[VERIFIED SOURCE]**: `mesh/http.mjs:173-178` makes `/readyz` a storage and wallet-auth readiness check. It does not check live quote access, provider terms, review grants, exact-action trial grants, proof, or settlement. `mesh/cfo/service.mjs:793-814` constructs owner-specific CFO readiness from provider/key flags, mandate and portfolio freshness, reviewer grants, T82 proof, open actions, and explicit-plan requirements; the result begins as `NO_DATA` and only changes to `BLOCKED` or remains `NO_DATA`. `web/dashboard/Cfo.jsx` currently validates overview readiness as `NO_DATA` or `BLOCKED` and separately presents provider readiness as `UNKNOWN` and execution readiness as `BLOCKED` (readiness render in the current component).

**[INFERRED]** Risk: a generic service health response, successful MCP/tool discovery, a local profile, or an overview response can be mistaken for provider availability or permission to move funds. The source distinguishes these concepts, but health/readiness evidence must not be promoted to an execution claim.

**[REPORTED]** Runtime limits: MCP 0.7.0/30 tools and an actual SDK smoke graph were reported; the graph had `executionReady:false`. Readiness was reported `ready`; these observations describe the reported endpoints, not a funded CFO path. Provider is reported disabled; review owners/grants/trials are reported zero; partner/sender keys are reported absent. The public dashboard is reported still gated/“Soon,” and the served guide 0.3.2; neither proves the R5 workflow is deployed or launch-ready. A previous unfunded production QA trace was reported but is not funded acceptance evidence. None of these runtime statements was independently verified here.

Required proof before release claims: parent-run exact-head CI and authenticated browser verification must show `NO_DATA` when dependencies/evidence are unavailable, no automatic capture/model/sign/relay, separate provider and execution gates, and no visual or API readiness state suggesting successful live financial execution. No funded or model-quality claim is authorized by these facts.

Severity basis: High for release/readiness claims; no source claim that a transaction bypass is currently exploitable.

- **[VERIFIED SOURCE]** Route authority: `mesh/http.mjs:303-356` exposes the existing CFO GET and POST routes only under a verified wallet session. `mesh/cfo/service.mjs:1123-1150` registers a signature only against the latest owner action in `PREPARED`/`NEXT_LEG_READY` state and validates it against the exact retained payload. Reconciliation preserves unknown states (`:1237-1303`). These are source controls, not proof of deployment or execution.
- **[VERIFIED SOURCE]** Read-side mutations: `mesh/cfo/service.mjs:735-763` shows overview can append housekeeping transitions by expiring unsigned preparation or closing blocked rotation entries. Those safe transitions are distinct from capture, model invocation, signature, or relay; the R5 read-recovery acceptance test should account for them.
- **[VERIFIED SOURCE]** Latest action head: `mesh/cfo/service.mjs:745-763` relies on backend newest-first owner sequence ordering, deduplicates by logical `actionId`, and may prepend a housekeeping transition. The UI helper and tests must preserve this ordering and not sort by timestamps or random IDs.
- **[VERIFIED SOURCE, not executed]** Helper regression cases: `web/test/cfo.test.mjs` loads the module namespace and invokes the new helpers from collected behavior cases.
